About & Cloud Architecture

Placement Surge Portal · AWS Free Tier · Region {{ aws_region|default("ap-southeast-2") }}

What this application does

Campus placement drives open with intense traffic spikes: approximately 3,000 students submit registrations in the same 60-second window. A traditional single-server architecture exhausts database connection pools, saturates CPU threads, or crashes entirely under this load.

This application decouples public entry, compute execution, and persistent storage so the portal remains operational and responsive under burst conditions, while costing zero dollars during idle periods on AWS Free Tier credits.

Cloud architecture

All resources reside within the default VPC across public subnets in multiple Availability Zones. Below is the system topology provisioned by CloudFormation.

Architecture flow summary

  1. Students access the portal through port 80 on the internet-facing Application Load Balancer (placement-surge-alb).
  2. The ALB is governed by alb-sg, allowing inbound HTTP traffic from 0.0.0.0/0.
  3. The ALB target group health-checks instances on /health every 10 seconds and distributes requests to healthy EC2 instances on port 8080.
  4. EC2 instances run in an Auto Scaling Group (placement-surge-asg) across public subnets in at least two Availability Zones (e.g. ap-southeast-2a and ap-southeast-2b).
  5. EC2 instances belong to app-sg, which strictly accepts traffic on port 8080 from alb-sg. Port 22 (SSH) is closed.
  6. Each instance runs a Gunicorn web server and an independent heartbeat process reporting CPU and status every 5 seconds to the placement-surge-fleet DynamoDB table.
  7. Registrations are written directly to placement-surge-registrations with a ConditionExpression to eliminate duplicate roll numbers.
  8. The instance IAM role grants least-privilege DynamoDB access, SSM parameter read for the admin token, and Session Manager shell management.
  9. CloudWatch monitors CPU, target health, and 5xx errors; alarms and ASG scaling events publish directly to an SNS topic for email notification.
  10. The entire stack is deployed idempotently via AWS CloudFormation (infra/infra.yaml).

Service model selection (IaaS / PaaS / SaaS)

Every cloud component was chosen to balance operational simplicity, horizontal elasticity, and zero-cost idle operation against AWS Free Tier constraints.

Component Model Why this choice Alternative considered
EC2 (t3.micro) IaaS Stateless virtual servers running custom Python/Gunicorn runtime with precise OS-level CPU and process control. AWS Lambda (higher cold-start latency under sudden burst; complex connection pooling).
Application Load Balancer Managed Service Native multi-AZ HTTP traffic distribution, automatic TLS offloading readiness, and health-check routing without managing Nginx servers. Self-hosted Nginx / HAProxy proxy server (single point of failure; requires manual failover).
Auto Scaling Group Managed Service Dynamic target-tracking scaling (CPU > 50%) and automated instance replacement when target health checks fail. Fixed instance fleet (wastes money during idle months; crashes when student surge exceeds capacity).
Amazon DynamoDB PaaS / Serverless On-demand billing (Pay-Per-Request) eliminates connection pool limits and supports atomic conditional writes for duplicate prevention. Amazon RDS PostgreSQL / MySQL (connection pool exhaustion at 3,000 students/min; hourly cost exceeds Free Tier).
Amazon SNS Managed Service Decoupled push notification pipeline delivering instance launch, termination, and alarm notifications to email with zero server configuration. Self-hosted Postfix SMTP server (complex DKIM/SPF maintenance; potential mail queue backpressure).
Amazon CloudWatch Managed Service Out-of-the-box infrastructure telemetry, detailed 1-minute metrics, metric alarms, and centralized operations dashboard. Self-hosted Prometheus / Grafana stack (adds billable compute and storage instances).
SSM Parameter Store Managed Service Encrypted SecureString storage for the administrative token with IAM-restricted access; avoids hardcoding secrets in git or user-data. Hardcoded environment variable in git (severe security risk) or AWS Secrets Manager (costs $0.40/month/secret).
AWS CloudFormation Infrastructure as Code Declarative, auditable template defining all 18 AWS resources for one-command provisioning and zero-leakage teardown. Manual AWS Console setup (error-prone; impossible to audit or teardown reliably).

Perspective note: From the students' point of view the portal is SaaS: they use it through a browser and manage nothing. We built it from IaaS and PaaS parts.

A single fixed server was rejected because it incurs non-stop cost while sitting idle for months, inevitably crashes during the first 60 seconds of a flash drive, and requires manual OS patching.

Features implemented

Load balancing across zones

ALB round-robins student requests across EC2 nodes in separate Availability Zones; visible in the Control Room node table and served-by footer.

Auto-scaling on CPU target

Target tracking scaling policy expands fleet from 2 to 4 nodes when average CPU exceeds 50%; visible in the session timeline chart.

Self-healing via health checks

Failing instances marked 503 are deregistered by ALB and terminated/replaced automatically by ASG; testable in the Control Room self-healing panel.

Multi-AZ fault tolerance

Instances and ALB subnets span multiple distinct zones; visible in the AZs serving metric and nodes list.

Automated email alerts

SNS topic dispatches immediate notifications for instance launches, terminations, high CPU, unhealthy targets, and 5xx spikes directly to subscriber inboxes.

Centralized operations dashboard

CloudWatch dashboard graphs in-service instances, fleet CPU, request count, p95 latency, healthy host count, and HTTP 5xx errors in 1-minute intervals.

Live control room

In-browser ops center polls node heartbeats every 3 seconds, displays an SVG timeline, probes load distribution, and logs lifecycle events.

Duplicate-safe registrations

DynamoDB ConditionExpression atomically rejects duplicate roll numbers per drive with HTTP 409; visible in the inline registration form error alerts.

Server-side eligibility checks

Validates applicant branch and minimum CGPA criteria before database writes; visible in inline validation errors and unit test suite.

Chained security groups & no SSH

App nodes only accept TCP 8080 from the ALB; port 22 is closed everywhere and shell access requires SSM Session Manager.

Input validation & strict CSP

Server-side field validation, 4 KB body cap, in-memory rate limiting (10/min), and strict Content-Security-Policy headers prevent injection attacks.

One-command deploy & load testing

Deploy script validates VPCs and launches CloudFormation; teardown audits zero remaining resources; loadtest script generates sustained traffic via Apache Bench.

Limits and future scope

Current constraints

  • HTTP only ingress: The portal runs over standard HTTP on port 80 until a custom domain name and AWS Certificate Manager (ACM) SSL certificate are attached.
  • Scale-out warmup latency: Because instances boot fresh Amazon Linux 2023 and install packages from scratch, provisioning a replacement or scaled-out node requires 2 to 3 minutes.
  • Single region deployment: The application operates exclusively in a single AWS region; an outage across all availability zones in that region would cause downtime.
  • Standard database backups: DynamoDB runs with default point-in-time recovery disabled to remain within free tier limits.
  • Baseline compute cost: Maintaining a minimum of 2 instances running 24/7 consumes approximately 1,440 instance-hours per month (covered during initial account trial credits, but billable beyond free hours).

Suggested future improvements

  • HTTPS via ACM & CloudFront: Provision an ACM certificate and front the Application Load Balancer with Amazon CloudFront CDN to cache static assets and terminate SSL at edge locations.
  • Pre-baked Golden AMIs: Build custom AMIs with Packer or EC2 Image Builder so new nodes boot in 15 seconds without running package installations during user data.
  • Scheduled scaling policies: Configure scheduled scaling actions before known registration deadlines (e.g. 08:55 IST) to pre-warm the fleet before traffic arrives.
  • Multi-Region DynamoDB Global Tables: Replicate registrations across secondary AWS regions for disaster recovery and geographic resilience.
